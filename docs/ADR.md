# Architecture Decision Records

## 철학
- **해커톤 MVP는 속도가 최우선이지만, 돈 계산과 권한은 타협하지 않는다.** 화면과 인프라는 가장 단순한 것을 고른다. 금액·정산·권한은 서버(SQL)와 테스트로 지킨다.
- **자체 서버를 두지 않는다.** Supabase(DB·Auth·Realtime·Storage·Edge Functions)와 Vercel(정적 웹)로 끝낸다.
- **웹 React 개발자가 처음 만드는 앱이다.** 웹과 비슷한 감각을 주는 도구(파일 라우팅, Tailwind, TanStack Query)를 고른다.
- **정답은 한 곳에 둔다.** 금액 확정과 순잔액은 서버가 계산한다. 클라이언트는 미리보기·송금 매칭·표시만 한다.

---

### ADR-001: Expo(React Native) SDK 57 + Expo Router + Development Build
**결정**
- Expo 관리형 워크플로우를 쓴다. SDK 57로 고정한다.
- 라우팅은 Expo Router를 쓴다.
- 실행은 Expo Go가 아니라 EAS Development Build로 한다.

**이유**
- React 경험을 그대로 쓸 수 있다.
- Expo Router는 파일 하나가 화면 하나라 Next.js App Router와 비슷하다. 딥링크(`/i/[token]`)가 라우트에 자동으로 연결된다.
- 음성 인식 같은 네이티브 모듈은 Expo Go에서 돌지 않는다. 처음부터 Development Build로 가야 나중에 갈아타지 않는다.
- EAS로 Mac 없이 iOS를 빌드할 수 있다. 다만 스토어 제출에는 Apple 개발자 계정이 필요하다.
- SDK 58은 2026-10-15에 나와 아직 2주밖에 안 됐다. 라이브러리(NativeWind, speech-recognition)가 따라왔는지 확인한 뒤에만 올린다.

**트레이드오프**
- 네이티브 대비 일부 성능을 포기한다.
- Development Build는 빌드에 10~20분이 걸린다. 그래서 네이티브 의존성이 바뀔 때만 다시 빌드하고, JS 변경은 Fast Refresh로 처리한다.

### ADR-002: Supabase가 유일한 백엔드, 쓰기는 RPC로만
**결정**
- Postgres(RLS로 읽기 제어) + `security definer` RPC(모든 장부 쓰기) + Edge Functions(외부 API·비밀값) + Realtime + Storage를 쓴다.
- 리전은 서울이다.
- 클라이언트는 장부 테이블에 직접 INSERT·UPDATE·DELETE를 하지 않는다.

**이유**
- PRD가 Supabase 기준이다. 실시간 피드·인증·파일 저장을 한 곳에서 해결한다.
- "멤버면 쓰기 가능" 같은 RLS로 두면 멤버가 PostgREST로 금액·이력·송금을 직접 고쳐 검증을 우회할 수 있다. 쓰기를 RPC로만 열어야 합계 검증·버전·이력이 강제된다.

**트레이드오프**
- 쓰기 로직이 plpgsql로 들어가므로 pgTAP 테스트가 필수다.
- Realtime은 끊긴 동안의 이벤트를 다시 보내주지 않는다. 재연결 시 전체 무효화로 보완한다.

### ADR-003: AI 인식은 Edge Function 안의 Claude 단일 호출 + JSON schema 구조화 출력
**결정**
- `parse-expense`가 사용자 권한으로 Storage에서 이미지를 읽는다.
- `claude-sonnet-5`(모델 ID는 Secrets `CLAUDE_MODEL`)에 보내고, **JSON schema 구조화 출력**으로 받아 zod로 다시 검증한다. 받는 값: 가게명·결제일·통화·품목(원문·번역·수량·금액·신뢰도)·원화 청구액·카드 끝자리·영수증 여부.
- 호출 조건: effort `low`, `max_tokens` 4096. 샘플링 파라미터(`temperature` 등)와 tool_choice 강제는 쓰지 않는다. 이 모델은 둘 다 거부한다.
- 텍스트(카드 문자·음성 결과)도 같은 함수와 같은 스키마로 처리한다.

**이유**
- API 키를 앱에 넣을 수 없다.
- 함수 하나와 스키마 하나로 입력 4종을 처리해 구현량이 가장 적다. 번역도 같은 호출에서 끝난다.
- Sonnet 5는 현행 모델 중 속도와 정확도의 균형이 가장 좋다.

**트레이드오프**
- 영수증 전용 OCR보다 숫자 인식이 덜 정확할 수 있다. 신뢰도 낮음 → '확인 필요', 품목 합계 ≠ 총액 → 조정 박스, 저장 전 확인 화면으로 보완한다.
- 고도화(CLOVA OCR·파파고, F4.8)는 이 함수 내부만 바꾸면 된다.
- 비용과 지연이 생긴다. 리사이즈(긴 변 1600px), effort low, 사용자·방 일일 한도, 클라이언트 자동 재시도 금지로 줄인다.
- 비용이 문제가 되면 `claude-haiku-5-5`를 영수증 세트로 비교해 본다(모델 ID만 바꾸면 된다).

### ADR-004: 음성 인식은 기기 내장 STT(expo-speech-recognition)
**결정**: PRD의 "Web Speech API" 대신 `expo-speech-recognition`(iOS SFSpeechRecognizer / Android SpeechRecognizer, ko-KR)을 쓴다. 서버에는 텍스트만 보낸다.

**이유**
- React Native 앱에는 브라우저 Web Speech API가 없다. Claude API는 오디오 입력을 받지 않는다.
- 기기 STT는 무료이고 빠르며, 음성 파일이 외부로 나가지 않는다.

**트레이드오프**
- 기기마다 정확도가 다르고, 일부 Android에는 인식 엔진이 없다. 실시간 자막을 보여주고 수정할 수 있게 하며, 엔진이 없으면 직접 입력으로 안내한다.
- 외국어 품목명이 섞이면 인식률이 떨어진다.
- iOS 최소 버전이 16.4가 된다.

### ADR-005: 인증 — 카카오(Supabase 기본) + 네이버(Supabase 커스텀 OIDC) + Apple(iOS)
**결정**
- 카카오(P0): `signInWithOAuth('kakao')` + 인앱 인증 세션 + **PKCE**(`flowType:'pkce'`, `detectSessionInUrl:false`).
- 네이버(해커톤 포함): Supabase **커스텀 OIDC 제공자** `custom:naver`(issuer `https://nid.naver.com`, scope `openid`). 0단계 PoC에서 RN 동작을 확인하고, 실패하면 P2로 미룬다.
- Apple(iOS, **스토어 출시 필수**): `expo-apple-authentication` + `signInWithIdToken`.
- 세션은 LargeSecureStore 패턴으로 저장한다.

**이유**
- 처음 안은 Edge Function이 네이버 코드를 교환한 뒤 magiclink 토큰을 앱으로 넘기는 직접 구현이었다. 이 방식은 토큰이 커스텀 스킴(`splito://`)으로 전달되므로 악성 앱이 가로채 계정을 탈취할 수 있었다. 서버 권한으로 세션을 만드는 위험도 직접 떠안아야 했다.
- Supabase가 2026-05부터 커스텀 OIDC를 지원하고, 네이버도 OIDC를 지원하므로 직접 구현할 이유가 없다.
- App Store 가이드라인 4.8에 따라 카카오·네이버만 제공하면 iOS 출시가 거절된다.

**트레이드오프**
- 카카오톡 앱으로 바로 로그인하는 경험(네이티브 SDK + `signInWithIdToken`)은 P1로 미룬다. 관련 이슈가 보고돼 있어 검증이 필요하다.
- 같은 사람이 여러 제공자로 가입하면 계정이 따로 생긴다(MVP에서 계정 통합 없음).
- 해커톤 데모는 카카오와 네이버(PoC가 성공했을 때)로 한다. Apple 로그인은 스토어 출시 전에 추가한다.

### ADR-006: 금액은 원 단위 정수, 확정은 서버가
**결정**
- 저장 타입: 원화 `bigint`, 외화 원본 `numeric(18,3)`, 환율 `numeric(18,6)`.
- `save_expense`가 서버에서 환율을 적용하고(0.5는 0으로부터 멀어지는 방향으로 반올림) 박스 원화를 최대 잔여 배분한다(동점이면 position 순).
- 나눗셈은 floor로 통일한다. 클라이언트 계산은 미리보기용이다.

**이유**
- 부동소수점 오차 1원이 "장부가 안 맞는다"는 불신으로 이어진다.
- JS와 Postgres는 음수 나눗셈·반올림 동작이 다르다(`Math.round(-2.5)` = −2, PG `round` = −3; bigint `/`는 0 쪽 버림). 정답을 한 곳에 두지 않으면 기기와 서버의 결과가 갈린다.
- 서버가 확정해야 오래된 앱이나 조작된 클라이언트가 임의 금액을 넣지 못한다.

**트레이드오프**
- 외화 박스의 원화가 "박스 외화 × 환율"과 1원씩 다를 수 있다. 그래서 근거는 지출 단위로만 보여준다.
- 미리보기와 저장 결과가 1원 다를 수 있다. 저장 후 화면은 서버 값으로 갱신한다.

### ADR-007: 정산안은 저장하지 않는다 — 서버 `room_balances` + 클라이언트 그리디 매칭, 송금은 장부 기록
**결정**
- 순잔액은 SQL 함수 `room_balances`가 유일한 정답이다. 박스 분배·자투리·공금·송금 기록을 모두 반영한다.
- 클라이언트는 이 결과에 결정적인 그리디 매칭만 적용한다.
- [보냈어요]·[받았어요]는 `transfers` 행으로 저장된다. 받을 사람이 확인한 것만 '정산 완료'·나가기·탈퇴 판정에 쓴다.

**이유**
- 정산 후 지출이 바뀌어도 남은 송금만 다시 나온다. 스냅샷을 무효화하는 규칙이 필요 없다(PRD 미결 Q의 답).
- 계산이 TS와 SQL 두 곳에 있으면 결과가 어긋날 수 있다. SQL 하나로 모은다.
- 거짓 [보냈어요]로 빚을 피해 나가는 것을 받을 사람 확인으로 막는다.

**트레이드오프**
- 정산 화면을 열 때마다 서버를 호출한다. 방 크기상 문제없다.
- 그리디는 최소 송금 횟수를 보장하지 않는다(최대 N−1회만 보장).
- 받을 사람이 확인하지 않으면 줄 사람이 방을 나갈 수 없다. "확인 대기" 표시로 확인을 유도한다.

### ADR-008: 초대는 128비트 토큰 링크 하나, 앱 미설치 경로는 Vercel 랜딩 + 플랫폼별 복원
**결정**
- 6자리 초대코드 UI를 두지 않는다(플로우 다이어그램 기준).
- 링크는 `https://{LINK_DOMAIN}/i/{token}`이다. iOS Universal Link, Android App Link로 앱을 연다.
- 도메인은 해커톤 동안 Vercel 기본 서브도메인(`splito.vercel.app`, 가칭)을 쓰고, 출시 전에 자체 도메인으로 바꾼다. 도메인이 바뀌면 앱을 다시 빌드해야 한다.
- 앱 미설치 경로:
  - Android: Play Install Referrer로 토큰을 복원한다.
  - iOS: 랜딩이 링크를 클립보드에 복사하고, 첫 실행 때 `ClipboardPasteButton`으로 붙여넣는다.
  - 둘 다 실패하면 링크 붙여넣기 입력을 보여준다.
- 랜딩은 방 정보를 조회하지 않는 정적 페이지다.

**이유**
- Firebase Dynamic Links는 종료됐다. 유료 SDK 없이 구현할 수 있는 가장 단순한 방법이다.
- 128비트 토큰은 추측할 수 없어 합류 시도 횟수를 제한할 필요가 없다.
- 랜딩이 방 이름을 보여주지 않으면 공개 API와 XSS 위험이 사라진다.

**트레이드오프**
- iOS 복원은 사용자가 버튼을 한 번 눌러야 한다. PRD의 "별도 입력 없이 이어서 합류"를 iOS에서는 "붙여넣기 한 번"으로 완화한다(H4로 검증).
- 도메인 구매와 AASA·assetlinks 설정이 필요하다.
- 해커톤 기간에는 스토어 출시 전이라 랜딩이 스토어 대신 내부 배포 링크(Android APK, iOS는 EAS 내부 배포 · 기기 등록 필요)로 보낸다. 이때 Play Install Referrer는 동작하지 않으므로, 해커톤에서는 두 플랫폼 모두 클립보드 붙여넣기로 초대를 복원한다.
- 6자리 코드를 빼는 것은 2026-10-28 인터뷰에서 확정했다.

### ADR-009: 환율 — 수출입은행 API를 Edge Function과 하루 단위 캐시로
**결정**
- `fx-rate`가 `oapi.koreaexim.go.kr`에서 날짜별 **전 통화를 한 번에** 받아 `fx_rates`에 캐시한다.
- 정규화: `JPY(100)`·`IDR(100)`은 100으로 나누고, 쉼표가 든 문자열을 파싱하고, CNY는 CNH로 매핑한다.
- 과거 날짜는 최대 10일 거슬러 가장 최근 고시일을 찾는다. 오늘이면서 고시 전이거나 API가 실패하면 pending이다.

**이유**
- API 키를 숨겨야 하고 일일 호출 한도(1,000회)가 있다. 날짜당 1회 호출이면 한도 걱정이 없다.
- 공휴일 달력을 관리하지 않아도 "고시된 직전 날짜"를 찾으면 직전 영업일 규칙이 만족된다.

**트레이드오프**
- 새 도메인의 SSL 체인 문제가 보고돼 있다. Deno fetch 동작을 0단계에서 확인하고, 실패해도 pending으로 안전하게 처리되게 한다.
- 일부 여행지 통화(VND·TWD·PHP 등)는 고시되지 않을 수 있다. 방 단위 수동 환율로 처리한다.
- 결제일은 영수증의 현지 날짜, 환율은 그날의 한국 고시값으로 정책을 고정한다(시차 때문에 하루 차이가 날 수 있다).

### ADR-010: NativeWind 4 + TanStack Query, 작성 중 지출은 기기에만
**결정**
- 스타일은 NativeWind 4.x(Tailwind 3), 데이터는 TanStack Query를 쓴다. Realtime 이벤트는 쿼리 무효화에만 쓴다.
- 인식 결과 확인 중인 지출(작성 중)은 DB에 넣지 않고 기기에만 둔다. 저장할 때 처음 INSERT한다.

**이유**
- 웹 경험을 그대로 쓸 수 있고, 상태 관리 라이브러리를 하나 줄인다.
- 작성 중 행을 DB에 두면 모든 쿼리·RLS·Realtime에 "저장됨이거나 내가 작성 중" 조건이 붙는다. 남겨진 행을 치우는 cron도 필요해진다.

**트레이드오프**
- 기기를 바꾸면 작성 중 지출이 이어지지 않는다.
- 업로드만 하고 저장하지 않은 사진(고아 파일)이 Storage에 남는다. 정리 작업으로 지운다(P1).
- NativeWind v5(RC)로는 나중에 이전해야 한다.

### ADR-011: 앱 없는 동행은 게스트 참여자로, 정산은 대표자에게 합산
**결정**
- 참여자를 `room_members.id`로 식별한다. 가입 멤버(`kind='user'`)와 게스트(`kind='guest'`, 이름 + 대표자)를 같은 테이블에 둔다.
- 장부의 모든 사람 참조(결제자, 대상 인원, 박스 지정, 공금 입금, 송금, 통장 주인)는 참여자 ID를 쓴다.
- 게스트의 순잔액은 대표자에게 합산해서 송금을 매칭한다. 게스트는 송금 당사자·통장 주인·방장이 될 수 없다.
- 게스트가 나중에 가입해도 계정으로 전환하지 않는다.

**이유**
- 주 대상인 가족 여행(부모님)과 SNS 계정이 없는 외국인 동행을 막다른 길 없이 지원한다(2026-10-28 인터뷰 결정).
- 대표자 합산은 공금 → 통장 주인 상계와 같은 구조라 정산 엔진에 새 개념이 필요 없다.
- 참여자 ID로 통일하면 "사람"을 가리키는 FK가 한 종류가 된다.

**트레이드오프**
- 게스트는 직접 송금 카드를 받지 못한다. 대표자가 대신 주고받는다.
- 게스트가 나중에 가입하면 박스를 다시 지정해야 한다(전환 기능 없음).
- 대표자를 바꾸면 과거 정산 귀속도 바뀐다. 경고와 이력으로 보완한다.
